# Checkpoint 低存储策略｜替换旧1710快照存档机制

## 每个run只保留有限权重

- `best_inference`: 最多一份长期保存的推理权重（若采用EMA则保存完整推理需要的EMA参数+必要normalizer、配置、编码器、GSA、TokenLearner参数）。用户的最终best是**五个指定评测位置中的最大SR**对应权重。
- `latest_resume`: 每个**仍在运行**的run保持最多一份可完整恢复的训练state（model/EMA/optimizer/scheduler/RNG/当前epoch或optimizer_step/配置）；安全原子替换旧版本。已完结run确认不再恢复后可清理其latest。
- `eval_snapshot`: 按五个指定评测位置产生的**临时推理权重**，只在独立eval任务排队与运行期间存在；评测全部episodes以及元数据已落盘、best权重安全更新、任务状态写为DONE之后才可删除。
- `best`提升时先写临时新文件并fsync/原子rename，再在确保新权重有效后删除旧best；不得先删除旧best。每run并列最佳选最早eval位置。
- 某个快照既是latest或best或其它作业依赖的文件时不可清理；做引用/占用检查。守护进程不可根据文件名模式大范围rm。

## 存储上限和队列回压

- 同时未评测快照数量建议从**每run不超过1个**、全局低并发（如最多4个）开始，按服务器实际单权重字节数、训练并行数和可用盘容量计算；积压达到上限时仅暂停相应run在下一个评测边界继续前进（run级backpressure），直到checkpoint被评测，不可丢评测点。
- 运行时按实际总磁盘占用报警（例如分配给本项目的剩余空间阈值），不要未经实测固定宣称150GB一定足够。若有多run的latest、数据缓存和训练日志，应按实测大小动态计算。
- 评测只需要225次而非1710次，长期存储不超过45个best推理权重+当前活跃run的latest训练权重，外加受限临时快照及轻量结果日志。全程保留数据/hash、每次评测的success记录、训练日志。

## 从旧执行包迁移：先审计再删除

1. 扫描旧1710条评测计划与历史checkpoint；新计划仅包含45×5=225条。保留原始文件备份与现有作业状态；不覆盖服务器真实运行中的manifest、不杀正在合规训练的任务。
2. 只有精确命中本次5个训练进度点、数据/配置/seed/环境可验证一致、且episode数完整的旧评测结果可以直接算作本次DONE；其它旧时间点评测移到`historical_evals`，不得参与Best-of-5。
3. 若既有run已经跨越某个新指定进度位置但没有留下可评测checkpoint，则不能凭空产生该位置SR。查找真实历史权重/恢复点后按协议补齐；确实无法补齐时将该run标为`NEEDS_REBUILD`，报告原因，不拿其他时点代替。
4. 所有临时权重必须满足：旧异步评测任务已不引用、现有best可恢复、非唯一latest、评测结果已真实固化、无进程打开该文件，**才进入安全删除白名单**。
5. 清理要有dry-run清单、逐文件字节数、SHA、引用源、删除时间与回收量；只有审计合格文件能删除。绝不递归删除checkpoint根目录。
